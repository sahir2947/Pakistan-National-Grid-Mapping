# Conformance tests for ports

If you re-implement part of pakgrid in another language, for example live
rider navigation in Dart inside a Flutter app, these files tell you whether
your version gives exactly the same answers as pakgrid.

| File | What it tests | Rules |
|---|---|---|
| [`navigation.json`](navigation.json) | Distance and direction to a target, compass names, turn words, distance text, and the navigation engine (GPS smoothing, heading choice, arrival) | [`NAVIGATION.md`](NAVIGATION.md) |

The files are generated by the Python library (`pakgrid export-conformance`),
and the repository's tests check that they are up to date and that the
JavaScript port in `viewer/pakgrid.js` passes them. You don't need Python to
use them.

## How to use it

1. Implement the rules in [`NAVIGATION.md`](NAVIGATION.md) in your language.
2. Write a small test that reads `navigation.json`, calls your functions with
   each case's inputs, and compares the results (below).
3. Run it in your CI. When pakgrid publishes a new version of the file, run
   it again.

[`runners/javascript.js`](runners/javascript.js) is a complete runner (about
90 lines) for the JavaScript port. Use it as the model for yours:

```console
$ node conformance/runners/javascript.js
OK: 1998 cases, 0 mismatches
```

## The file

```json
{
  "format": "pakgrid-conformance", "suite": "navigation", "format_version": 1, "grid_version": 1,
  "tolerance": {"metres": 1e-06, "degrees": 1e-09, "coordinates": 1e-12},
  "field_tolerance": {"distance_m": "metres", "bearing_deg": "degrees", "lat": "coordinates", "…": "…"},
  "compass": [...], "turn_words": [...], "format_distance": [...], "metres_per_degree": [...],
  "direction": [...], "sessions": [...]
}
```

| Section | Each case | Call |
|---|---|---|
| `compass` | `bearing_deg` → `compass`, `compass_short` | The compass names of a bearing (NAVIGATION.md §2) |
| `turn_words` | `turn_deg` → `turn` | §3 |
| `format_distance` | `metres`, `units` (`"m"` or `"ft"`) → `text` | §4 |
| `metres_per_degree` | `lat` → `lat_m`, `lon_m` | §1 |
| `direction` | `from` `[lat, lon]`, `to` `[lat, lon]`, `heading` (number or null) → `expected` | §2 |
| `sessions` | `target` `[lat, lon]`, `options`, `steps` | §5: create a session, then make each step's call and compare the state with `expect` |

A session step is `{"call": ..., "args": {...}, "expect": {state}}`:

| `call` | `args` |
|---|---|
| `add_fix` | `lat`, `lon`, `accuracy`, `speed`, `heading` (each may be `null`), `time` |
| `add_compass` | `heading`, `time` |
| `set_position` | `lat`, `lon`, `heading` (may be `null`) |
| `set_target` | `lat`, `lon` |
| `reset` | none |

`options` holds only the options a session changes from their defaults
(NAVIGATION.md §5). Times are seconds.

**Comparing.** For each field of an expected result: if the expected value is
a number and the field is listed in `field_tolerance`, your number must be
within that tolerance (`tolerance[field_tolerance[field]]`); otherwise the
value must be exactly equal (strings, `null`, and inputs passed through).

**NaN.** JSON has no NaN, so an input that is NaN (a broken sensor reading) is
written as the string `"NaN"`. Turn it into your language's NaN before calling.

**Ties.** Random cases never lie within 1e-6 of a decision threshold, so a
correct port gets the same words on any platform. Exact ties are tested only
with inputs given directly (NAVIGATION.md §6). Expect the tie cases to catch
two common porting mistakes: rounding halves away from zero instead of to
even, and a `%` operator that keeps the sign of negative numbers.
